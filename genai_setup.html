01

Introduction

What this guide is, who it is for, and how it is organized

Robotics projects are hard. Not because any single piece is impossible, but because you are simultaneously managing hardware, firmware, operating systems, Python environments, and communication protocols. A servo that does not respond could be a wiring issue, a serial permission error, a bad baud rate, or a logic bug in code you wrote an hour ago. Most project hours disappear while you isolate which layer is failing.

Generative AI coding agents — such as Claude Code, GitHub Copilot, Cursor, and Ollama — change what is possible for a student working alone or in a small team. They can read your entire codebase, explain unfamiliar code, generate hypotheses about why something is broken, suggest fixes, and help you write better code faster. Used well, they compress the feedback loop between “something is wrong” and “I understand what is wrong and how to fix it” from hours to minutes.

Used poorly — pasting errors without context, accepting suggestions blindly, or treating the agent as a search engine — they waste time and introduce bugs you do not understand. This guide teaches you how to use them well.

This guide is for students in robotics courses at UC San Diego’s Jacobs School of Engineering and Halicioğlu Data Science Institute working on a robotics project involving a Raspberry Pi, hardware, and Python or ROS 2 code. It does not assume prior experience with AI coding tools, Git, or Linux systems. You do not need to be a software engineer. You need to be curious, willing to read error messages carefully, and willing to use AI tools as thinking partners rather than answer machines.

This guide covers four things:

  • How to set up your environment: Git, GitHub, SSH keys, VS Code Remote SSH, and your AI coding agent of choice.
  • Git and GitHub fundamentals: version control to avoid losing work and collaborate safely.
  • How to connect to and develop on your robot: working over SSH and using VS Code Remote SSH to make the Pi feel local.
  • How to use GenAI tools effectively: prompting, debugging, review, and where LLMs fit into robotics beyond writing code.

The guide is structured as a linear workflow. Each section builds on the last. You move between three environments:

  • Your laptop, where you write code, run your AI agent, and manage Git.
  • GitHub, where your code is backed up and version-controlled in the cloud.
  • The Raspberry Pi, where your code runs on real hardware.

One note on expectations: AI coding agents are powerful but not infallible. They hallucinate imports, miss edge cases, and sometimes suggest changes that look plausible but introduce subtle bugs. A core theme of this guide is learning to use these tools critically — understanding what they produce, verifying it, and catching mistakes before they become problems on the car.

✦
Key message
Use AI as a thinking partner: understand the code, verify the fix, and catch mistakes before they become problems on the vehicle.

Prerequisites / Environment Setup

Install the tools you need before you begin working on the robot

Installing Git locally

Git is the version control system that tracks every change you make to code. It is how your laptop, GitHub, and Raspberry Pi stay in sync. Everything else in this guide depends on it.

First, check whether Git is already installed:

Check Git
git --version

If you see a version string, you are ready. If you get “command not found,” install Git for your OS:

Install Git
# macOS
xcode-select --install
# or
brew install git

# Linux (Ubuntu/Debian)
sudo apt update && sudo apt install git

# Windows
# Download Git from https://git-scm.com/download/win

After installing, tell Git who you are. Use the same email as your GitHub account:

Git identity
git config --global user.name "Your Name"
git config --global user.email "you@ucsd.edu"
git config --global --list
ℹ
Windows note
When installing Git on Windows, choose “Checkout as-is, commit Unix-style line endings.” This prevents line-ending conflicts when your code runs on the Linux-based Raspberry Pi.

GitHub account setup

GitHub is where the DonkeyCar project lives publicly, where your fork will live, and where you will submit your pull request.

1
Create an account
Go to github.com/signup. Use your UCSD email address so you can access the Student Developer Pack.
2
Verify your email
Check your UCSD inbox for a verification email and click the link before trying to push code or open a pull request.
3
Activate the Student Developer Pack
Visit education.github.com/pack and verify your UCSD enrollment. This gives you free GitHub Copilot and related tools used in this guide.
4
Enable 2FA
Use an authenticator app rather than SMS. GitHub requires this for accounts that push code.

If you already have a GitHub account with a personal email, you do not need to create a new one. Add your UCSD email as a secondary address so GitHub can verify your student status. Then activate the Student Developer Pack on that account. The benefits apply to the account, not the email address alone.

SSH key generation for GitHub

SSH keys let your laptop authenticate with GitHub without typing a password every time you push code. You generate a key pair: a private key that stays on your machine and a public key that you give to GitHub.

⚠
Important
Never share your private key (id_ed25519). The public key (id_ed25519.pub) is the one you paste into GitHub.

Check whether you already have a key:

Check existing SSH keys
ls ~/.ssh

If there is no key, generate one:

Generate SSH key
ssh-keygen -t ed25519 -C "you@ucsd.edu"

# Accept the default file location by pressing Enter
# Optionally add a passphrase; otherwise press Enter to skip it

eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

# macOS only
ssh-add --apple-use-keychain ~/.ssh/id_ed25519

Then copy the public key and add it to GitHub:

Add SSH key to GitHub
# macOS
cat ~/.ssh/id_ed25519.pub
pbcopy < ~/.ssh/id_ed25519.pub

# Windows (Git Bash)
clip < ~/.ssh/id_ed25519.pub

# Test the connection
ssh -T git@github.com

Then go to github.com/settings/keys, click “New SSH key,” paste the public key, and click “Add SSH key.” The test command should show a success message like “Hi <your-username>! You’ve successfully authenticated.”

Git/GitHub Fundamentals

The concepts and commands you should know before making changes

Git is software that runs on your laptop. It tracks changes to your codebase over time and lets you save snapshots of your work called commits, create branches, and restore earlier versions if something breaks. GitHub is a website that hosts Git repositories in the cloud so your team can share and review code.

ConceptWhat it means
RepositoryThe full project folder with code, history, and configuration tracked by Git.
ForkA personal copy of someone else’s repository on GitHub under your account.
CloneDownload a repository from GitHub to your laptop.
BranchA parallel line of development where you can make changes without touching the main code.
CommitA saved snapshot of your changes with a description.
PushUpload your local commits to GitHub.
PullDownload changes from GitHub to your local machine.
Pull RequestA proposed change to merge your branch into another repository.
UpstreamThe original repository you forked from, such as github.com/autorope/donkeycar.

Git commands cheat sheet:

Git commands
# Get code
git clone <url>
git fetch upstream

git pull

# Work on branches
git branch
git checkout -b <branch-name>
git checkout <branch-name>

# Save changes
git status
git diff
git add <file>
git add .
git commit -m "Your message here"

# Sync your fork
git push origin <branch-name>
git push -u origin <branch-name>
✓
Helpful tip
If you cannot remember a Git command, ask your AI agent: “What is the Git command to [do what I want]?” This is one of the best uses of an AI coding agent — Git syntax is hard to memorize and easy to look up.

Connecting to the Robot

Connect to the Pi, add hotspots, and work directly from VS Code

Connecting to new hotspots

The Raspberry Pi on your DonkeyCar is pre-configured to connect to the campus Wi-Fi network. When you are in the lab, your laptop joins the same network and can reach the Pi directly by IP address. If you want to develop off-campus, add your home Wi-Fi or phone hotspot to the Pi first while still on campus.

Option A — Add your network via terminal:

Add network via Pi terminal
sudo nmcli device wifi connect "YourNetworkName" password "YourPassword"
nmcli connection show

Option B — Edit the config file:

wpa_supplicant config
sudo nano /etc/wpa_supplicant/wpa_supplicant.conf

network={
   ssid="YourNetworkName"
   psk="YourPassword"
   priority=1
}

Save the file, then reboot the Pi using sudo reboot for the changes to take effect.

VS Code Remote SSH

VS Code Remote SSH lets you open the Raspberry Pi’s filesystem directly inside VS Code on your laptop. You get full syntax highlighting, your extensions, and an integrated terminal that runs commands on the Pi.

1
Install the Remote-SSH extension
Open VS Code, press Ctrl+Shift+X or Cmd+Shift+X, search for Remote-SSH, and install the Microsoft extension.
2
Add the robot as a new host
Open the Command Palette and run Remote-SSH: Add New SSH Host. Enter ssh pi@ucsdrobocars-DSC-T# and replace # with your team number.
3
Connect
Choose the host and enter the Pi password. The first time, VS Code installs the Remote-SSH server on the Pi.
4
Open the repo folder
Once connected, open the folder containing your cloned DonkeyCar fork. In the integrated terminal, run hostname to confirm you are on the Pi.

Development with Generative AI

Prompt for explanation, minimal changes, and verification

AI coding agents are not search engines. The quality of what they produce depends almost entirely on the quality of the context you give them. The strategies below work regardless of which tool you picked.

  • Give the agent the full file, not just the error. Pasting only an error message forces the agent to guess at context. Paste the relevant file or class alongside the error.
  • Tell the agent what the code is supposed to do. This clarifies intent before a fix is proposed.
  • Ask for explanation before asking for a fix. Start by asking what a function does, then ask how to fix it or why it fails.
  • Request the minimal change. Ask for the smallest edit that fixes the problem without broad rewrites.
  • Ask the agent to explain its own suggestion. If it cannot explain the code it proposes, do not trust it yet.
  • Use the agent for rubber duck debugging. Describe the problem as if you are explaining it to a colleague. This often surfaces the answer before the agent responds.
✦
Review process
Before accepting a suggestion, read it line by line, compare it to the original, check imports, run it, and ask the agent to review its own fix for edge cases.

The most important habit is simple: never paste AI-generated code into the codebase without reading and understanding every line first. If you cannot explain why each line exists, you are not ready to push it.

Using your AI agent as a development partner

Use the agent proactively, not just reactively. Start every session with a context dump: paste the relevant files, describe what you are trying to do, and explain what you changed or discovered previously. Use it to plan before code, not after code. Ask it to anticipate review feedback and narrate unexpected behavior as soon as something goes wrong. This keeps the loop short and prevents the agent from operating on incomplete context.

Example context prompt
I'm working on a VESC steering bug. Here are the relevant files. I am trying to fix the bug where steering values can exceed -1 to 1. Yesterday I traced the issue to the run() method in vesc.py but haven't made the fix yet. Help me think through the right approach before I start editing.

Debugging Strategies

Use a structured debugging loop with the robot hardware in mind

Read the full traceback before doing anything else

When DonkeyCar crashes, Python prints a traceback. The single most common debugging mistake is reading only the last line — the exception message — and immediately pasting that into the agent. The last line tells you what went wrong. The lines above it tell you how the code got there. Always paste the full traceback.

Read it yourself first, from the bottom up:

  • The bottom line is the exception type and message.
  • The lines immediately above it show the function and line number where it crashed.
  • The lines above those show the chain of calls that led there.

Ask yourself: does the crash location make sense given what I just changed? Is this in my code or in DonkeyCar internals? Answering these questions before involving the agent often surfaces the answer before you even finish typing the prompt.

Hypothesis-first debugging loop

When you paste an error into your agent, do not just ask “How do I fix this?” Ask it to generate hypotheses first:

Hypothesis prompt
"Here's the full traceback and the relevant code. Before suggesting a fix, give me three possible root causes ordered by likelihood. For each one, tell me how I would verify whether that is actually the problem."

This forces a diagnostic step before a solution step and gives you a mental model of the problem rather than a command to run blindly.

Hardware vs. software triage

Many time sinks on the Pi are really hardware problems, and vice versa. Before diving into code, run through this triage:

  • Is the problem consistent or intermittent? Consistent failures are usually software. Intermittent ones often point to hardware or environment issues such as loose cables, power instability, or serial dropouts.
  • Did it ever work? If the code worked yesterday and does not today, suspect hardware or environment first.
  • Is the error in your code or in DonkeyCar internals? Look at the traceback: if the crash is in a file you did not touch, your change may be passing a bad value into an existing function rather than causing a bug in the function itself.

Quick hardware checks before deeper software debugging:

Quick hardware checks
ls /dev/ttyACM*
ls /dev/video*
vcgencmd get_throttled
free -h
df -h

Paste the output of suspicious checks into your agent along with your error. Hardware state context greatly improves the quality of the diagnosis.

Debugging serial and hardware communication

If your change touches the VESC, servo, or any hardware interface, new failure modes appear that pure software debugging will not catch.

  • Baud rate and port mismatches: the VESC communicates over serial at a specific rate, and the port or configuration must match.
  • Timing issues: code that works at low speed may fail under load because commands arrive faster than the hardware can process them.
  • Permission errors on device files: if you see PermissionError when opening /dev/ttyACM0, the user likely needs DBus or dialout access.
Permission fix
sudo usermod -aG dialout $USER
# Log out and reconnect for the group change to take effect

Reading logs when there is no traceback

Sometimes the car crashes without printing anything useful. A few techniques help recover useful information:

Log output to a file
cd ~/mycar
python3 manage.py drive 2>&1 | tee drive_log.txt

After a crash, open the log file and look at the last few lines before the exit. You can also inspect the system log:

System journal
journalctl -n 200 --no-pager

Another low-tech approach is temporary print() statements at relevant points in the logic so you can trace execution and identify where it fails. Remove them before committing.

Using your agent for rubber duck debugging

Sometimes you do not have an error — you have unexpected behavior. The car drives but pulls left, the model performs worse than before, or the camera feed is frozen. These are harder to debug because there is no traceback to paste. The most effective approach is to describe the issue precisely and completely as if you are explaining it to a colleague.

Rubber duck prompt
"Here's what I expected to happen: ...
Here's what actually happened: ...
Here's what I changed since it last worked correctly: ...
Here's the relevant code and terminal output: ..."

The act of writing this prompt carefully often surfaces the answer before the agent responds. When it does not, the agent has exactly the information it needs to generate useful hypotheses instead of generic suggestions.

Real Example: Debugging ROS 2 Hardware Integration with Claude Code

A realistic robotics debugging workflow using AI to narrow the hypothesis space

The best way to understand how to use an AI coding agent for robotics debugging is to see it applied to a real problem. This section walks through representative issues from a UCSD ROS 2 project involving a Raspberry Pi 5, a VESC controller, an OAK-D Lite camera, a joystick, and Cartographer SLAM.

The stack included:

  • Raspberry Pi 5 running Ubuntu 24.04
  • VESC motor controller connected over USB serial
  • OAK-D Lite depth camera
  • Joystick controller
  • ROS 2 Jazzy
  • Cartographer SLAM for mapping
  • DonkeyCar framework for vehicle control

Problem 1: Cartographer launch file error

After ROS 2 was installed, the next step was setting up Cartographer. The launch file from a reference implementation failed with a parameter not present in the installed version. The error read:

Cartographer error
[cartographer_node-1] terminate called after throwing an instance of
'std::invalid_argument'
[cartographer_node-1] what(): /home/pi/ros2_ws/src/cartographer_config/config/racecar_2d.lua:32: unknown field 'use_landmarks'

Claude Code was given the full traceback, the launch file, and the Lua configuration file. It identified that use_landmarks was a parameter introduced in a later version of Cartographer and then flagged two additional incompatible parameters. This prevented a second debugging session later on. The fix was a corrected Lua config file with the incompatible parameters removed and comments explaining the version-specific settings.

Problem 2: VESC serial permission error

After SLAM was working, the VESC script failed with:

VESC permission error
PermissionError: [Errno 13] Permission denied: '/dev/ttyACM0'

When the team pasted the error, the relevant Python section, and the output of ls -la /dev/ttyACM0, Claude Code identified that the Pi user was not in the dialout group, which owns serial device files on Ubuntu. The fix was:

VESC fix
sudo usermod -aG dialout $USER
# log out and reconnect

This is a classic Linux permissions issue: the Python code was not necessarily wrong, but the user lacked access to the USB serial device.

Problem 3: OAK-D Lite camera not detected after ROS 2 launch

The OAK-D Lite camera worked in the standalone depthai Python library but failed when launched through the ROS 2 node. The error was vague:

OAK-D error
[depthai_ros_driver-2] [ERROR] [1723478234.521]: Failed to find device after 30.0s timeout

Claude Code suggested two ordered hypotheses:

  1. The ROS 2 node was being launched as a different user than the one with USB access permissions to the OAK-D device.
  2. The depthai library version installed in the ROS 2 workspace did not match the version installed system-wide.

It suggested checking both possibilities and verifying each one independently. In this case, the second hypothesis was correct: the system-wide depthai version was 2.24, while the ROS 2 workspace had sourced an older version. Pinning the workspace to the correct version resolved it.

⚠
Patterns across all problems
The missing information was almost never just the last line of the error. In robotics debugging, the answer often depends on a configuration file, a terminal output snippet, or a permission check several layers upstream. AI agents are most useful when they are asked to identify hypotheses and verification steps, not just guess fixes.
